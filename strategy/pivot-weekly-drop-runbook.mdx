## Purpose

The **weekly drop push** nudges Pivot users when a new catalog week is live. It is **not** the publish gate — users see published events whenever they open the app via `GET /pivot/feed`. The push is the reminder to open **PivotWeek** and start swiping.

Drop timing is **configurable per city** (and per week via overrides) in `TenantConfig`. Do **not** rely on a hardcoded Thursday 6pm constant in ops memory or scripts.

Related docs:

- [Pivot MVP implementation plan — Task 6.3](/strategy/pivot-mvp-implementation-plan#task-63--manual-weekly-drop-push-runbook-config-driven)
- [Pivot MVP implementation plan — Weekly drop schedule](/strategy/pivot-mvp-implementation-plan#weekly-drop-schedule-configurable)
- [Pivot metadata contract](/strategy/pivot-metadata-contract) — `batchWeek` and catalog publish fields
- [Native-first city discovery](/strategy/pivot-native-first-discovery-plan) — Discover finds sources; **Refresh all** recrawls them. Do not Discover on drop day.
- [Just Go organizer identity](/strategy/just-go-organizer-identity-plan) — city Catalog (`?page=4`), backfill, merge leftovers, claim before Creator Console

<Note>
**Pilot default (suggestion only):** When provisioning a new Pivot city, seed **Thursday 18:00** in the tenant's local timezone (e.g. `America/New_York` for NYC). That gives users Thu–Sun to browse before weekend events. Change defaults or one-off weeks in **Platform Admin** — never in mobile or push copy.
</Note>

## Push copy (Just Go voice)

| Field | Text |
| --- | --- |
| **Title** | `just go*` |
| **Body** | `What are you doing this week? Just go.` |

Tapping the notification must open **PivotWeek** (not campus `EventDetails`). Payload requirements (Task 6.2):

- `data.edition` / `data.appEdition`: `'pivot'`
- `data.type`: `'pivot_week'`
- `data.navigation.route`: `'PivotWeek'` (or deep link `meridian://pivot/week`)

## Tenant drop config (source of truth)

Each Pivot city row in **`TenantConfig`** stores:

| Field | Notes |
| --- | --- |
| `pivotDropTimezone` | IANA zone (e.g. `America/New_York`) |
| `pivotDropDayOfWeek` | `0` = Sunday … `4` = Thursday … `6` = Saturday |
| `pivotDropHour` | Local hour `0–23` |
| `pivotDropMinute` | Local minute (default `0`) |
| `pivotDropOverrides[]` | Optional `{ batchWeek, dayOfWeek, hour, minute }` when one week moves |

Backend helper: `resolvePivotDropInstant(tenant, batchWeek)` in `Meridian/backend/utilities/pivotDropSchedule.js` — override wins over default; returns UTC `dropAt`.

**Where ops reads "Next drop":**

1. **Platform Admin → Tenant management** — pivot tenant detail / metadata (Task 0.4)
2. **Pivot Lab** — city header for the selected `batchWeek`

If the schedule moved, update **`pivotDropOverrides`** or the default fields in Platform Admin **before** sending. Do not send from calendar memory.

## Ops sequence (curate → release → push)

After the [release gate](/strategy/pivot-tenant-ops-dashboard-plan#batch-release-model) (Phase 3):

1. **Curate early** — Recrawl saved jobs into the target `batchWeek` as **`staged`** (Curation → Saved jobs → **Refresh all**, or per-job **Run for week**). Do **not** re-run city **Discover** for a weekly Luma/venue refresh — that searches for new sources and spends Firecrawl search credits. Staged events never appear in `GET /pivot/feed`.
2. **Release before drop** — Explicit **Release week** (`POST .../batches/:batchWeek/release`) flips `staged` → `published`. Emergency Lab path: “Stage & release now…” with typed `RELEASE_NOW`.
3. **Send the push** — At the resolved drop instant (below). The push is still only a nudge; the feed already shows released events.

Do **not** treat Lab “Stage” as live-deck publish.

## Organizer Catalog (city graph)

Curation is a **week** release queue. **Catalog** is the weekless organizer graph for the city — who we ingested, leftovers, and who can open Creator Console onto that catalog.

Surface: `/platform-admin/pivot/:tenantKey?page=4`  
Unlinked: `?page=4&filter=unlinked` · Ambiguous names: `?page=4&filter=ambiguous` · Dossier: `?page=4&organizerId=`  
Plan: [Just Go organizer identity](/strategy/just-go-organizer-identity-plan)

<Steps>
  <Step title="Refresh / crawl first">
    After **Refresh all** or a curation job run, new events get `host.organizerIds` at publish (resolve unique hosts **once per crawl**). Catalog updates from that attach — **no extra weekly job**. Do not run city Discover just to refresh hosts.
  </Step>
  <Step title="Backfill once per city">
    First time on a city (or after merge-rule changes): Catalog **Backfill**, or from `Meridian/backend`:

    ```bash
    npm run backfill:pivot-organizers -- --tenant=nyc
    ```

    Re-run with **Force re-resolve** / `--force` only after resolver or merge rules change. Skip when `host.organizerIds` is already an array (including `[]` leftovers). **Do not** recrawl historical `sourceUrl`s or Firecrawl from this button.
  </Step>
  <Step title="Merge leftovers — leave soup unlinked">
    Open **Unlinked**. Confirm a fuzzy proposal or pick source → target (path id is the **kept** organizer; body `{ sourceOrganizerId }`).

    **Merge** when two rows are the same person/brand (shared profile, unique folded name, or a proposal with venue / title / image corroboration).

    **Leave unlinked:** joined `Alice & Bob` display strings, venue-as-host, one-off names, and colliding `normalizedName` with no hard ID. Do not invent a brand from a soup string. Two organizers claimed by **different** users cannot merge (`ORGANIZER_ALREADY_CLAIMED`).
  </Step>
  <Step title="Claim before inviting a creator">
    1. Grant the user on the tenant **Creators** allowlist (active `PivotCreatorGrant` for that city).
    2. Claim the organizer (platform admin). Catalog has no claim form yet:

    ```bash
    POST /admin/pivot/tenants/:tenantKey/organizers/:organizerId/claim
    { "globalUserId": "<GlobalUser id>" }
    ```

    Requires an **active** grant (`CREATOR_GRANT_REQUIRED` otherwise). Already claimed by someone else → `ORGANIZER_ALREADY_CLAIMED`. Unclaim: same path `{ "unclaim": true }`, then claim again to reassign. Does **not** rewrite scraped `source` or `createdByUserId`.
    3. Then invite them to Creator Console. They see host-created listings **and** scraped events on claimed organizers (scraped rows are read-only + insights).
  </Step>
</Steps>

<Warning>
Do not re-Firecrawl history to recover dropped host ids. Audience on a dossier is a **live query**, not a weekly rollup. Consumer cards still show `host.name`.
</Warning>

## Pre-send checklist

Complete these steps **in order** for the target city and `batchWeek`:

<Steps>
  <Step title="Stage then release catalog">
    Confirm that week's events are **`ingestStatus: published`** (after Release) with the correct **`customFields.pivot.batchWeek`**. Curate as `staged` days before the drop; **Release** before send. The push is the nudge, not the gate.
  </Step>
  <Step title="Read resolved drop time">
    Open **Platform Admin** or **Pivot Lab** and note **Next drop** for the target `batchWeek` (from `resolvePivotDropInstant`). Verify timezone, day, and local time match ops intent.
  </Step>
  <Step title="Adjust schedule if needed">
    If this week moved (holiday, delay, A/B timing), add or edit a `pivotDropOverrides` row — or change the tenant default — then re-read **Next drop** to confirm the displayed instant updated **without a code deploy**.
  </Step>
  <Step title="Send at drop instant">
    At the resolved local instant (or manually if ops intentionally moved the slot), send the push targeting **`pushAppEdition === 'pivot'`** tokens for that `tenantKey` only.
  </Step>
  <Step title="Verify on a pilot device">
    Confirm one pilot device receives the notification and tapping it lands on **PivotWeek** with the new week's deck.
  </Step>
</Steps>

## Send options

### Option A — Backend script (recommended)

From `Meridian/backend`:

```bash
# Preview recipients + payload without sending
npm run send:pivot-weekly-push -- --tenantKey=nyc --batchWeek=2026-W22 --dry-run

# Send at the configured drop window (warns if now is >30 min from dropAt)
npm run send:pivot-weekly-push -- --tenantKey=nyc --batchWeek=2026-W22

# Override timing guard (e.g. ops moved slot and already confirmed in Platform Admin)
npm run send:pivot-weekly-push -- --tenantKey=nyc --batchWeek=2026-W22 --force
```

Script behavior:

- Loads tenant drop config from global **`TenantConfig`**
- Resolves **`dropAt`** via `resolvePivotDropInstant`
- Warns if **`now`** is more than 30 minutes from **`dropAt`** (unless `--force`)
- Warns if zero **published** catalog events exist for the `batchWeek`
- Sends only to users with **`pushAppEdition: 'pivot'`** and a registered Expo push token
- Uses Just Go copy and **`pivot_week`** navigation payload above

Implementation: `Meridian/backend/migrations/sendPivotWeeklyPush.js`

### Option B — Firebase / Expo console

Use when script access is unavailable:

1. Filter or target **pivot edition** device tokens for the city tenant (same cohort that registered with `appEdition: 'pivot'`).
2. Use the [Push copy](#push-copy-just-go-voice) above.
3. Include custom data: `edition: pivot`, `type: pivot_week`, `navigation.route: PivotWeek`, or deep link `meridian://pivot/week`.

<Warning>
Console sends bypass publish-count and drop-window checks. Run the [Pre-send checklist](#pre-send-checklist) manually.
</Warning>

## Troubleshooting

| Symptom | Likely cause | Action |
| --- | --- | --- |
| Script aborts "outside drop window" | Sending far from resolved `dropAt` | Re-check Platform Admin / Lab **Next drop**; use `--force` only after confirming schedule |
| "No pivot push tokens found" | No devices registered pivot edition | Have pilot users open Pivot app while logged in (registers token with `pushAppEdition: 'pivot'`) |
| Push opens campus screen | Payload missing `edition: 'pivot'` or wrong route | Use script or match Task 6.2 payload shape |
| Wrong drop day/time displayed | Stale tenant config | Update `pivotDropOverrides` or defaults in Platform Admin; re-read **Next drop** |
| Deck empty after tap | Catalog not published for `batchWeek` | Publish events in Pivot Lab first |

## Crew ritual dry run (Task 6.4 / mobile Phase 12)

Before submitting a ritual-capable store build, run the automated matrix and complete manual staging checks.

### Automated

From `Meridian/backend`:

```bash
npm run dry-run:pivot-crew-ritual
```

Scenarios covered: **solo**, **one crew**, **three crews**, **split decide**, **invited-only**.

Print staging checklist only:

```bash
node migrations/pivotCrewRitualDryRun.js --checklist
```

### Manual staging (required before App Store submit)

1. Install **staging binary** (sends `X-App-Version`, uses ritual routes on Week).
2. Point at **staging API** with gated `GET /pivot/week-ritual`.
3. Confirm `config.mobile.minAppVersion` is **below** staging binary version (no false force-update).
4. Solo: drop dashboard → deck → personal recap.
5. Crew: join/create → Week dashboard with crew highlight → swipe → Week hub decide cards → per-crew decide room → recap with crew outcomes first.
6. Three crews: open each your-move/waiting card from the hub (async quorum; not a single pager pass).
7. Invited-only: roster shows invited placeholders; quorum excludes them.

### Release sequence reminder

1. Deploy backend (ritual routes + `minAppVersion` below live store version).
2. Submit store build.
3. After build is searchable: set `minAppVersion` to new store version + `forceUpdate: true`.
4. **Rollback:** revert `minAppVersion` first; binary rollback is last resort.

See [Pivot ritual deprecation ticket](/strategy/pivot-ritual-deprecation-ticket) for legacy route removal after adoption.

### Ritual funnel metrics (mobile)

Client emits `pivot_ritual_funnel` with `step`:

| Step | Meaning |
| --- | --- |
| `dashboard` | Drop dashboard visible (crew Week) |
| `deck_complete` | Personal deck exhausted |
| `decide_open` | Decide room opened (hub deep-link or room mount; per `crewId`, includes `hubState`) |
| `decide_complete` | Viewer confirmed or crew locked (per `crewId`; `completeReason` = `confirm` \| `lock`) |
| `recap` | Ritual recap phase rendered |

Confirm/swap still emit `pivot_crew_judgement_confirm` / `pivot_crew_judgement_swap` with `hubState` + `judgementStatus`.
