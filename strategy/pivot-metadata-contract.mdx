## `customFields.pivot` on Event

Pivot catalog events are **normal `Event` documents** in the tenant (city) database. Pivot-specific metadata lives under `customFields.pivot` — not a separate collection or event type.

### Schema

```json
{
  "batchWeek": "2026-W21",
  "source": "luma",
  "sourceUrl": "https://lu.ma/example-event",
  "host": {
    "name": "Brooklyn Board Game Cafe",
    "imageUrl": "https://example.com/host-avatar.jpg",
    "profileUrl": "https://partiful.com/u/example-host",
    "organizerIds": [],
    "identities": [
      {
        "provider": "partiful",
        "externalId": "example-host",
        "profileUrl": "https://partiful.com/u/example-host",
        "name": "Brooklyn Board Game Cafe",
        "imageUrl": "https://example.com/host-avatar.jpg"
      }
    ]
  },
  "tags": ["board-games", "social"],
  "ingestStatus": "staged",
  "importedAt": "2026-05-20T14:30:00.000Z",
  "importedBy": "ops@meridian.study"
}
```

Host-created (Just Go Creator Console) example:

```json
{
  "batchWeek": "2026-W21",
  "source": "justgo",
  "platformManaged": false,
  "createdByUserId": "665c00000000000000000002",
  "creatorSubmittedAt": "2026-05-18T16:00:00.000Z",
  "host": {
    "name": "Maya Chen",
    "imageUrl": "https://example.com/maya.jpg",
    "identities": [
      {
        "provider": "justgo",
        "name": "Maya Chen",
        "imageUrl": "https://example.com/maya.jpg"
      }
    ]
  },
  "tags": ["social", "board-games"],
  "ingestStatus": "draft"
}
```

### Field reference

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `batchWeek` | `string` | **Yes** (`staged` / `published`) | ISO week: `YYYY-Www` (see below). **Default at ingest:** ISO week of the event’s start date (or first time slot). Optional `forceBatchWeek` pins to an explicit week. |
| `source` | `"luma" \| "partiful" \| "manual" \| "justgo"` | Recommended | Where the event came from. **`justgo`** = created in Just Go Creator Console (host self-serve). Do **not** overload `manual` for host create. |
| `sourceUrl` | `string` (URL) | Recommended | Original listing URL; often same as `externalLink` |
| `host.name` | `string` | **Yes** (`staged` / `published`) | Display snapshot for cards. **Not a unique key** — do not unique-index this string. Different sources emit variants (`Gabe's` / `Gabes`); identity lives on `organizerIds` / `identities`. |
| `host.imageUrl` | `string` (URL) | No | Avatar or logo for the display host. Prefer persist when a parser has one; do not clobber a known URL with `null`. |
| `host.profileUrl` | `string` (URL) | No | Link to host profile on Partiful/Luma. Prefer persist when a parser has one. |
| `host.organizerIds` | `string[]` | No (empty until resolved) | `PivotOrganizer._id` values. Union on event dedup merge. Absent until crawl/backfill resolve (Phase 2+). |
| `host.identities` | `object[]` | No | Captured at preview even before an organizer exists. One row per person/org — do not collapse into the joined `host.name`. |
| `tags` | `string[]` | Recommended (`staged` / `published`) | Catalog slugs from **Pivot tag catalog** (see below); used by ranker, Lab, and chips |
| `ingestStatus` | `"draft" \| "staged" \| "published"` | **Yes** | Lifecycle — see [Ingest status lifecycle](#ingest-status-lifecycle) |
| `importedAt` | ISO-8601 datetime | Recommended | When ops ingested the event (scrape / Lab) |
| `importedBy` | `string` | Recommended | Global user ID or ops email (scrape / Lab) |
| `platformManaged` | `boolean` | Recommended for `justgo` | **Always `false` in Phase 1.** Reserved for Phase 2 native ticketing / in-event. Consumer app must not branch on this until Phase 2. |
| `createdByUserId` | `string` | Recommended for `justgo` | Global or tenant user id of the creator who submitted the listing |
| `creatorSubmittedAt` | ISO-8601 datetime | Recommended for `justgo` | When the host submitted into curation |

`host.identities[]` item:

| Field | Type | Notes |
| --- | --- | --- |
| `provider` | `'luma' \| 'partiful' \| 'generic-site' \| 'justgo' \| 'manual'` | Source of this identity |
| `externalId` | `string?` | Native host id / slug when known. Do **not** invent one for `generic-site`. |
| `profileUrl` | `string?` | Canonical profile URL (`partiful.com/u/…`, `luma.com/user/…`) |
| `name` | `string?` | Raw name from this identity (not the joined display string) |
| `imageUrl` | `string?` | Avatar for this identity |

Curation and analytics filter host self-serve on `source === 'justgo'` (and/or `createdByUserId` present).

<Warning>
**Staged and published catalog events must have `batchWeek` and `host.name`.** Ingest QA should reject stage/release if either is missing. Draft events may omit them until ready. **New ingest must not auto-set `published`** — see [Ingest defaults](#ingest-defaults).
</Warning>

### Ingest status lifecycle

| `ingestStatus` | Meaning | In `GET /pivot/feed`? | Ops UI |
| --- | --- | --- | --- |
| `draft` | Imported / crawled / host-submitted; incomplete or unreviewed | **No** | Curation / Lab review queue (includes Host-created) |
| `staged` | Ready for the target `batchWeek`; waiting for explicit release | **No** | Curation “ready for drop” |
| `published` | Released for that week’s live deck | **Yes** | Live catalog |

```text
crawl / import  →  draft
review + tags   →  staged          (still hidden from feed)
Release week    →  published       (bulk flip; feed-eligible)

host create (Just Go Creator)  →  draft   (configurable; see below)
                               →  never auto-published
```

**Feed eligibility rule (Choice A — event-only):**

> `GET /pivot/feed` (and `findPublishedPivotEvent` helpers) require `customFields.pivot.ingestStatus === 'published'` (plus existing `batchWeek`, `host.name`, window filters).  
> **Release** = ops action that bulk-updates `staged` → `published` for a `(tenantKey, batchWeek)`.  
> There is **no** separate batch flag required for feed reads in v0.  
> Host-created (`source: 'justgo'`) events use the **same** rule — no special feed path until ops release.

Choice B (batch `released` **and** event `staged|published`) was considered and **rejected for v0** — more moving parts for the same ops outcome. Optional `PivotBatch` still tracks ops progress; it does **not** gate the feed under Choice A.

### Ingest defaults

| Action | Default `ingestStatus` |
| --- | --- |
| New URL / explore crawl / JSON import (Lab ingest) | **`staged`** when host + tags valid (Lab requires tags); never auto-`published` |
| Incomplete / unreviewed rows | `draft` (edit modal / future crawl without tags) |
| **Just Go Creator Console host create / submit** | **`draft`** (tenant `creatorPublish.defaultIngestStatus`; may be overridden to `staged` for trusted pilots). **Never** auto-`published`. |
| “Release week” API | bulk `staged` → `published` |
| Emergency “Stage & release now” (`releaseNow` + confirm `RELEASE_NOW`) | `published` on create |

Do **not** treat Lab “Stage for city” or Creator submit as live-deck publish — keep **Release** separate ([Pivot tenant ops dashboard plan](/strategy/pivot-tenant-ops-dashboard-plan) Phase 3). Ops sequence: [weekly drop runbook](/strategy/pivot-weekly-drop-runbook#ops-sequence-curate--release--push).

### Creator publish config (`creatorPublish` on tenant)

Stored on pivot tenant settings (sparse overrides; missing keys → defaults). Resolved via `resolveCreatorPublishConfig(tenant)` in `utilities/pivotCreatorPublishConfig.js` / `services/pivotCreatorPublishConfigService.js`.

| Key | Type | Default | Meaning |
| --- | --- | --- | --- |
| `defaultIngestStatus` | `'draft' \| 'staged'` | `'draft'` | Status on host create/submit. Pilot default must remain `draft`. **Not** `'published'`. |
| `weekAssignment` | `'event_start' \| 'force'` | `'event_start'` | How `batchWeek` is chosen |
| `forceBatchWeek` | `string?` | unset | Only when `weekAssignment === 'force'` |
| `requireTagsToSubmit` | `boolean` | `false` | If true, block submit until catalog tags present |
| `notifyAdminsOnCreate` | `boolean` | `true` | Notify ops on new host draft |
| `notifyAdminsOnLiveWeekSubmit` | `boolean` | `true` | Extra emphasis when target week already has published events / is released |

**Week rule for host create (locked):**

1. **Default (`weekAssignment: 'event_start'`):** `batchWeek` = ISO week of the event’s `start_time` (else first `timeSlots[].start_time`) — same as Lab ingest.
2. **Force:** `weekAssignment: 'force'` + `forceBatchWeek` pins every create to that week.
3. **Already-released / live week:** still land as `draft` for that `batchWeek`; never auto-`published`. Ops stage/release (or move week). Helpers: `computeCreatorBatchWeek(eventStart, config)`.

### Migration (existing catalog)

| Existing rows | Behavior |
| --- | --- |
| Already `ingestStatus: 'published'` (current or past weeks) | **Leave as `published`.** No mass rewrite required. Feed behavior unchanged for live decks. |
| New imports after the gate ships | Default **`staged`**; appear in feed **only after** explicit Release (or emergency `RELEASE_NOW`). |
| Future weeks already wrongly published early | Ops may **unrelease** (`published` → `staged`) via admin API — document danger if users already swiped. |

Task 3.3 landed: ingest create defaults to `staged`; `published` on create requires `releaseNow` + `confirm: "RELEASE_NOW"`.

### ISO week format (`batchWeek`)

Use **ISO 8601 week date** format: `YYYY-Www`

- `YYYY` — ISO week-numbering year (may differ from calendar year near January)
- `W` — literal separator
- `ww` — zero-padded week number (`01`–`53`)

Examples: `2026-W21`, `2026-W01`, `2025-W52`

**Assignment at crawl / manual ingest (locked):**

1. **Default:** `batchWeek` = ISO week of the event’s `start_time` (else first `timeSlots[].start_time`). One crawl or batch import may land events in many weeks.
2. **Override:** request body `forceBatchWeek: true` + `batchWeek` pins every write to that week.
3. **Undated:** fall back to provided `batchWeek`, else current ISO week.

Helpers: `resolveEventBatchWeek` / `batchWeekFromEventDate` in `utilities/pivotIsoWeek.js`.

JavaScript (reference):

```javascript
function toIsoWeek(date = new Date()) {
  const d = new Date(Date.UTC(date.getFullYear(), date.getMonth(), date.getDate()));
  d.setUTCDate(d.getUTCDate() + 4 - (d.getUTCDay() || 7));
  const yearStart = new Date(Date.UTC(d.getUTCFullYear(), 0, 1));
  const week = Math.ceil((((d - yearStart) / 86400000) + 1) / 7);
  return `${d.getUTCFullYear()}-W${String(week).padStart(2, '0')}`;
}
```

## `PivotBatch` (optional ops record)

Per-city week progress for Curation readiness and release auditing. **Does not gate the feed under Choice A** — feed still keys only off event `ingestStatus === 'published'`.

**Storage (preferred):** tenant (city) DB, registered via `getModelService`, accessed with `connectToDatabase(tenantKey)` + `getModels({ db }, 'PivotBatch')` from platform-admin routes. Alternative: global DB with unique `(tenantKey, batchWeek)` — document if chosen.

### Shape

```json
{
  "tenantKey": "brooklyn",
  "batchWeek": "2026-W28",
  "status": "curating",
  "targetEventCount": 40,
  "releasedAt": null,
  "releasedBy": null
}
```

| Field | Type | Notes |
| --- | --- | --- |
| `tenantKey` | `string` | City key (required if stored globally; implied by DB if tenant-scoped) |
| `batchWeek` | `string` | ISO week `YYYY-Www` |
| `status` | `"curating" \| "ready" \| "released"` | Ops progress only |
| `targetEventCount` | `number` | Optional readiness target for the drop |
| `releasedAt` | ISO-8601 datetime \| `null` | Set when Release succeeds |
| `releasedBy` | `string` \| `null` | Platform admin user id / email |

**Status mapping (ops, not feed):**

| `PivotBatch.status` | Typical event states for that week |
| --- | --- |
| `curating` | Mix of `draft` / `staged`; none or few `published` for this future week |
| `ready` | Enough `staged` events; awaiting Release |
| `released` | Release ran; matching events flipped to `published` |

Upsert on first curation activity for `(tenantKey, batchWeek)`. Release API should set `status: 'released'`, `releasedAt`, `releasedBy` **and** bulk-update events `staged` → `published`.

## Pivot tag catalog

Published event `customFields.pivot.tags` **should** use slugs from the global **Pivot tag catalog** (`PivotTagCatalog` in the platform DB). The catalog is the single vocabulary shared by Lab ingest, mobile onboarding, user interests, and feed ranking.

### Catalog row shape (platform DB)

| Field | Type | Notes |
| --- | --- | --- |
| `slug` | `string` | Lowercase kebab-case, unique (e.g. `live-music`, `board-games`) |
| `label` | `string` | Human copy for chips and onboarding (“live music”, “board games”) |
| `sortOrder` | `number` | Display order in pickers |
| `active` | `boolean` | When `false`, hidden from `GET /pivot/tags` but still valid on legacy events |

Seed idempotently: `npm run seed:pivot-tag-catalog` (from `Meridian/backend`).

### `GET /pivot/tags`

Authenticated Pivot clients fetch the active catalog:

```json
{
  "success": true,
  "data": {
    "tags": [
      { "slug": "live-music", "label": "live music" },
      { "slug": "board-games", "label": "board games" }
    ]
  }
}
```

- Requires `verifyToken` (same as other `/pivot/*` routes).
- Returns only **`active: true`** rows, sorted by `sortOrder` then `slug`.
- Inactive slugs remain valid on events already published; they are omitted from onboarding/Lab pickers until reactivated.

### Tag validation rules

| Context | Rule |
| --- | --- |
| **Event stage / release (Lab / Curation)** | Each tag must be an **active** catalog slug; stage/release requires ≥1 tag (`400 TAGS_REQUIRED`). Optional **Claude tag suggestion** via `POST /admin/pivot/ingest/suggest-tags` when `ANTHROPIC_API_KEY` (or `CLAUDE_API_KEY`) is set in backend env. |
| **User interests** | Subset of **active** catalog slugs only; max 8 (Task 8.2) |
| **Feed payload** | Returns `tags[]` as stored on the event (may include inactive slugs on legacy rows) |
| **Slug format** | Lowercase kebab-case: `^[a-z0-9]+(?:-[a-z0-9]+)*$` |

### `GET /pivot/profile/interests`

Authenticated Pivot clients load saved interest tags:

```json
{
  "success": true,
  "data": {
    "interestTags": ["live-music", "board-games"]
  }
}
```

- Requires `verifyToken`.
- Returns `[]` when the user has not set interests yet.

### `PUT /pivot/profile/interests`

Body:

```json
{
  "interestTags": ["live-music", "board-games"]
}
```

Response:

```json
{
  "success": true,
  "data": {
    "interestTags": ["live-music", "board-games"]
  }
}
```

- Slugs are normalized (trim, lowercase), deduped, and capped at **8** (`400 INTEREST_TAGS_LIMIT` if exceeded).
- Unknown or inactive slugs → `400 INVALID_TAG`.
- `interestTags: []` clears interests (skip onboarding / profile reset).
- Stored on tenant `User.pivotInterestTags`; campus `/update-user` is unchanged.

<Warning>
Do not invent ad hoc tag strings in mobile or Lab. Unknown slugs are rejected at publish and interest save time once Tasks 8.2 and 8.4 land.
</Warning>

## Catalog host model (display vs technical)

Pivot uses two host layers on the same `Event` document:

| Layer | Storage | Shown in Pivot UI? |
| --- | --- | --- |
| **Display host** | `customFields.pivot.host` | **Yes** — primary label on cards and detail |
| **Technical host** | `hostingId` → per-city **Pivot Catalog** org (`hostingType: 'Org'`) | **No** — satisfies Events-Backend required fields only |

**Do not** create a new `Org` per venue. **Do not** show “Meridian [city]” as the public host label.

**Do not** unique-index `host.name`. **Do not** attribute organizers with a weekly job — crawl-time extract + resolve-once, then stamp at publish. Historical rows use the same resolver (backfill); do not re-Firecrawl `sourceUrl`s to recover dropped host ids.

### Organizer identity (`PivotOrganizer`)

City-scoped collection `pivotOrganizers` via `getModels` — **not** a campus `Org`. See [Just Go organizer identity](/strategy/just-go-organizer-identity-plan).

| Field | Type | Notes |
| --- | --- | --- |
| `tenantKey` | `string` | City; denormalized for queries |
| `canonicalName` | `string` | Best display name |
| `normalizedName` | `string` | Lowercase, punctuation-folded; unique **when claimed as exact alias** — not globally unique |
| `aliases[]` | `{ name, normalized, source? }` | Observed strings |
| `kind` | `'person' \| 'brand' \| 'venue' \| 'unclear'` | Default `unclear` |
| `identities[]` | same shape as `host.identities` + `confidence` | Hard IDs live here |
| `imageUrl` | `string?` | |
| `claimedByUserId` | `ObjectId?` | GlobalUser; claim is a later phase |
| `claimStatus` | `'unclaimed' \| 'pending' \| 'claimed'` | Default `unclaimed` |
| `lastResolvedAt` | `Date` | Last crawl or backfill touch |

Do **not** store weekly audience rollups on this document in v0.

#### Resolution tiers

| Tier | Signal | Action |
| --- | --- | --- |
| 1 — hard ID | Normalized `profileUrl` or `(provider, externalId)`; `justgo` + `createdByUserId` | Auto-create / attach |
| 2 — exact alias | `normalizedName` unique in this city | Auto-attach if unique; else ambiguous |
| 3 — corroborated fuzzy | Name similarity + shared venue **or** recurring title **or** same image | **Propose** only — ops confirm in Catalog |
| 4 — leftover | Co-host soup, venue-as-host, one-offs | **Leave unlinked** — do not invent a brand from a one-off string |

Tickets live on `externalLink` (Partiful/Luma URL). Campus `EventCard` paths that read `hostingId.org_name` are unchanged; Pivot clients must use `displayHost` from API responses.

## `displayHost` API shape

Pivot APIs resolve **`displayHost`** from `customFields.pivot.host` so mobile never reads `hostingId.org_name`.

### Source mapping

| `displayHost` field | Source |
| --- | --- |
| `name` | `customFields.pivot.host.name` (**required**) |
| `imageUrl` | `customFields.pivot.host.imageUrl` (optional) |
| `profileUrl` | `customFields.pivot.host.profileUrl` (optional) |

Consumer `displayHost` does **not** grow `organizerIds` or `identities` in this plan. Cards still show the display snapshot only.

  "data": {

### Rules

- **`displayHost.name` is always present** for published catalog events in the feed. Server should omit or reject events missing `host.name` at ingest QA time.
- **`hostingId` and org name are not returned** to Pivot mobile clients (or are stripped from the payload).
- Same `displayHost` shape applies to **`GET /pivot/week-recap`** and event detail endpoints.
- Campus event APIs are unchanged; they continue to use org/host resolution as today.

### Explore (same catalog)

`GET /pivot/explore` (Phase 2) uses the **same published + `batchWeek` + pilot window** candidate set as feed, same serializer family (`displayHost`, tags, `userIntent`), and the same `PivotEventIntent` store. Canonical enums, response sketch, and non-goals: [Explore product + API contract](/strategy/just-go-explore-embeddings-plan#explore-product--api-contract-task-01). Scroll-past in Explore is not a pass; push/drop opens Week, not Explore.

**Intent reconcile (Task 2.3):**

| Field | Values |
| --- | --- |
| `events[].userIntent` | `interested` \| `registered` \| `passed` \| `null` — same as feed; week-scoped via `batchWeek` on `PivotEventIntent` |
| `filters.excludePassed` | Default `true`; when true, passed events are omitted from `events[]` |
| `intentBadgePriority` | `["registered", "interested", null]` — client badge precedence (going → interested → unset) |

Passed on the Week deck suppresses the event in Explore by default. Interested and registered events remain listed with `userIntent` set. Pass `excludePassed=false` to include passed rows (each still carries `userIntent: "passed"`).

### Event indexes for Pivot feed / Explore (Task 1.4)

Defined on tenant `Event` schema (`Meridian/backend/events/schemas/event.js`). Partial on `customFields.pivot.batchWeek` (string) so campus-only rows stay out of the index.

| Index name | Keys | Covers |
| --- | --- | --- |
| `pivot_batchWeek_ingestStatus_start_time` | `customFields.pivot.batchWeek`, `customFields.pivot.ingestStatus`, `start_time` | `GET /pivot/feed` and `GET /pivot/explore` equality on week + published, then time window / sort |
| `pivot_batchWeek_ingestStatus_tags` | `customFields.pivot.batchWeek`, `customFields.pivot.ingestStatus`, `customFields.pivot.tags` | Explore tag filters + Lab week catalog scans |

Feed query shape (same prefix as Explore v0):

```text
{ batchWeek, ingestStatus: 'published', status ∈ …, isDeleted ≠ true, host.name, pilot window on start_time / timeSlots }
sort: registrationCount ↓, start_time ↑  (then in-process rank)
```

Expected plan: IXSCAN on `pivot_batchWeek_ingestStatus_start_time` (equality week + ingestStatus; `start_time` supports the pilot window range). Tag-filtered Explore can use `pivot_batchWeek_ingestStatus_tags`.

### Feed sort pipeline (Tasks 8.6 + 8.8 + crew 3.1 + rules_v1 decks)

After the DB pre-sort (`registrationCount` desc, `start_time` asc), `getPivotFeed` scores every eligible published event for the user (`rankerVersion: rules_v1`), then **selects a short deck** instead of returning the full city week.

Numeric score (tenant `pivotDeckConfig` knobs; defaults shown):

```text
friendGoing × friends going                         default 1.5
+ friendInterested × friends interested             default 0.5
+ crewSignal × (1.5 × crew going + crew interested) default 0.2
+ personalInterest × |event.tags ∩ user.pivotInterestTags|  default 0.7
+ crew interest bleed                               ≤ interestBleed.maxWeight (crew config)
− negativeTag × |event.tags ∩ tagsFromLowRatedEvents|       default 0.4
then start_time ↑ as a tie-break
```

Length (defaults: soft max **15**, hard max **18**):

1. If fewer eligible events than `softMax`, return all of them (do not pad).
2. Otherwise take the top `softMax`.
3. Keep extra cards while `score >= max(Nth_score × leewayRatio, highScoreFloor)` (defaults `0.85` / `0.7`), up to `hardMax`.
4. Never exceed `hardMax`.

Membership is frozen on first `GET /pivot/feed` per `userId + batchWeek` (`PivotDeckSnapshot`). Later loads return those IDs (still published and upcoming) in frozen order. Admin `?refresh=true` rebuilds. Changing `pivotDeckConfig` does not reshuffle already-frozen decks. Ops edit knobs on the city dashboard **Drop deck** page (`PUT /admin/platform/tenants/:tenantKey` with sparse `pivotDeckConfig`). The same page can inspect a user’s deck via `GET /admin/pivot/tenants/:tenantKey/drop-deck/preview` — that preview never writes a snapshot; `rebuild=true` ignores freeze. Explore and admin next-drop preview still see the full published catalog.

- **Crew signal:** Count **active** crew members (excluding self and `invited` placeholders) with week-scoped `PivotEventIntent` on the feed `batchWeek`. Members in multiple shared crews dedupe to one count per event. Deck `crewSignal` comes from `pivotDeckConfig.weights.crewSignal` (cached ≤60s). Crew `feedMix.crewSignalWeight` still drives Explore `for_you` lexicographic sort (`rules_v0`).
- **Interest bleed (Task 3.2):** When `crew.interestBleed.enabled`, union `pivotInterestTags` from active crew members (same eligibility as crew signals). Tags already in the viewer’s personal interests are excluded from bleed. Bleed adds `min(overlap × maxWeight, maxWeight)` (default `maxWeight: 0.15`). When `requiresCrewMemberSwipe` is `true`, only tags from members with any `PivotEventIntent` on the feed `batchWeek` count. Disabled bleed → zero contribution.
- **Crew social proof (Task 3.3):** Optional `crewInterestedCount` / `crewRegisteredCount` on feed events — deduped active crew member intents for the feed `batchWeek`. Omitted when zero. Registered increments both counts (same as friends). Mobile deck cards render scrapbook chips when present.
- **`PivotInteraction` crew eval (Task 3.4):** Deck `impression` rows optionally include `crewIds[]` (viewer’s active crew ids) and `crewConfigVersion` (shipped `crew.version`). Server-enriched on `POST /pivot/interactions/impressions`; omitted when the user has zero crews. Existing consumers ignore unknown fields.
- **Registered vs interested:** Same as friends — `registered` increments both crew registered and crew interested counts; `interested` increments crew interested only.
- **Interest overlap** uses exact catalog slug equality (case-normalized). Events with no tags get overlap `0` (neutral, not penalized).
- **Negative-tag penalty** loads the user's prior `pivot_event` feedback with `rating < 3`, collects catalog slugs from those events' `customFields.pivot.tags`, and subtracts `negativeTag` per overlap. That can **drop** a card out of a capped deck (unlike `rules_v0`, which only used the penalty as a sort tier).
- Untagged feed events always get penalty `0`.

### Mobile tag chips (Task 8.5)

Deck cards, event detail hero, and week recap rows render **`PivotTagChips`** from feed `tags[]`:

| Surface | Max chips | Interest highlight |
| --- | --- | --- |
| Swipe card / detail hero | 3 | Accent fill when slug ∈ `user.pivotInterestTags` |
| Week recap row | 1 (compact) | Same accent rule |

- Labels come from catalog slug formatting (`board-games` → `board games`).
- When `tags` is empty, mobile shows a single **`type`** chip if `event.type` is set; otherwise the chip row is hidden.

### Profile interests edit (Task 8.7)

Authenticated users edit saved interests from **Profile → your interests** (`PivotEditInterests` screen):

- Pre-fill from `GET /pivot/profile/interests` (falls back to auth user payload on load failure).
- Save via `PUT /pivot/profile/interests`; allows `[]` to clear interests (unlike onboarding, which requires ≥1 tag or skip).

- Analytics: `pivot_interests_updated` with `{ count }`.

## `PivotEventIntent` (attendee intent)

For MVP, **creators live on Partiful/Luma**. Meridian stores **intent**, not ticket confirmation. Do not reuse campus `attendees` rows as “going” unless status is explicitly `registered`.

### Collection shape (tenant DB)

```json
{
  "_id": "665b1b2c3d4e5f6789012346",
  "userId": "665c00000000000000000002",
  "eventId": "665a1b2c3d4e5f6789012345",
  "batchWeek": "2026-W21",
  "status": "interested",
  "updatedAt": "2026-05-21T18:00:00.000Z"
}
```

**Unique index:** `(userId, eventId)`

### Status enum

| Status | Meaning | UI copy | Friend-facing |
| --- | --- | --- | --- |
| `interested` | Swipe right / tap Interested | “Interested” | “X friends interested” |
| `registered` | User tapped “I got a ticket” (self-report v0) | “Going” | “X friends going” |
| `passed` | Swipe left | — | — |

### Intent vs campus RSVP

| Action | MVP behavior |
| --- | --- |
| Swipe right | Set `interested` — **do not** open external URL |
| Swipe left | Set `passed` |
| “Get tickets” (detail / recap) | Open `externalLink`; log `pivot_external_open` |
| “I got a ticket” | Set `registered` via `POST /pivot/intent/:eventId/registered` |

**Social copy:** use **interested** vs **going** (registered). Only `registered` counts as friends **going**.

### Related APIs

| Endpoint | Purpose |
| --- | --- |
| `POST /pivot/feed/action` | `{ eventId, action: "interested" \| "pass" }` |
| `GET /pivot/week-recap` | User’s `interested` events for `batchWeek` |
| `POST /pivot/intent/:eventId/registered` | Self-confirm ticket (optional `openedExternalAt`) |

## Manual ingest checklist

When pasting events into the tenant DB (or before Lab/Curation release):

1. Set tenant (city) DB and **Pivot Catalog** `hostingId` for that city.
2. Set `status: 'not-applicable'`, `visibility: 'public'`, `externalLink` to Partiful/Luma URL.
3. Set `customFields.pivot.batchWeek` to the ISO week of the event’s **actual start date** (default). Only force a different week when intentionally overriding.
4. Set `customFields.pivot.host.name` to the **real organizer** from the listing.
5. Set `customFields.pivot.ingestStatus`:
   - `'draft'` or `'staged'` while curating (default for new imports).
   - `'published'` **only** when releasing that week to the live deck (or legacy rows already live).
6. Verify: staged/draft events do **not** appear in `GET /pivot/feed`; after release to `published`, they appear with correct `displayHost.name`.
