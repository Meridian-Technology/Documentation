## Purpose

Make Relay a faithful compute handoff for the same phased workflow used on the laptop:

```text
one canonical plan
  → one implementation agent per phase
  → one prompt per implementation step
  → one verification bundle per phase
  → one read-only contract judge per phase
  → one durable phase capsule
  → one review transition to the next phase
```

The desired outcome is comparable implementation quality and completion semantics when a plan runs on Relay Mini or locally. Exact latency and model output will still differ by machine and vendor, but the plan, context, verification, and completion contract must be the same.

<Warning>
This is a Relay runner/planning refactor. It does not authorize a Mini deployment, a LaunchAgent restart, changes to production compute-job behavior, or execution of notification jobs on Relay.
</Warning>

## Decisions already made

| Area | Decision |
| --- | --- |
| Canonical artifact | The rich laptop MDX is the only authored plan. Relay derives its execution snapshot from it. |
| Implementation sessions | One implementation agent session per phase; one turn per step. |
| Verification | Run a phase-level command bundle after all implementation steps, with explicit per-command working directories. |
| Judge | One read-only, phase-level contract judge. It substitutes for human due diligence and must prevent false-complete/sloppy work. |
| Context | Persist a bounded, structured phase capsule. The next phase gets the canonical source plus completed-phase capsules. |
| Gates | Never require consecutive approvals without agent work. Approving a completed phase starts the next phase unless that next phase explicitly has exceptional pre-start review. |
| Mixed packages | A phase may cover backend and frontend work. Verification commands must declare their own `cwd`; no implicit inherited package is allowed. |
| Compatibility | Existing Relay Markdown plans remain runnable during migration. New plans use the canonical format. |

## Current problems to eliminate

1. A laptop MDX and a Relay Markdown file duplicate the same intent, and the Relay version loses decisions, file context, task completion rules, and constraints.
2. Relay executes step-level tests and a fresh judge for every step, rather than verifying a complete phase.
3. Relay resends the whole execution plan and unbounded previous step output on later turns; the next phase receives only the final-step narrative.
4. A plan-level `phase-approve` combined with phase `approve-before` creates two stops per phase.
5. A phase that spans packages can silently verify from an inherited, wrong working directory.

## Non-goals

- Change compute worker contracts, schedules, outbox behavior, or production apply semantics.
- Run Meridian notification sends on the Mini.
- Remove old plan support before canonical compilation, migration tooling, and acceptance coverage are complete.
- Claim model-output determinism across vendors or machines.
- Add a second implementation-model call solely to write a phase handoff.

## Before starting

1. Work from the Relay checkout: `cd relay`.
2. Use the Node version required by `relay/package.json`.
3. Preserve unrelated dirty work in all sibling repositories.
4. Run focused tests with `npx vitest run <files>`; run the complete Relay suite before a merge candidate.
5. Do not use `relay-handoff` until a later, explicitly approved deployment/acceptance plan says to stage the resulting execution plan on the Mini.

## Data model target

The internal execution snapshot should have a versioned representation equivalent to:

```ts
type PhaseVerify = {
  cwd: string;
  command: string;
  label?: string;
};

type PhaseGate = "auto" | "review-after" | "approve-before";

type PhaseCapsule = {
  version: 1;
  canonicalPlanSha256: string;
  phaseNumber: number;
  phaseTitle: string;
  completedSteps: Array<{ number: number; instruction: string }>;
  changes: { commits: string[]; files: string[]; diffStat: unknown };
  verification: Array<{ cwd: string; command: string; exitCode: number; outputTail: string }>;
  decisions: string[];
  deviations: string[];
  blockers: string[];
  judge: { verdict: "pass" | "fail"; summary: string; checks: string[] };
};
```

Raw transcripts and full logs remain durable audit artifacts, but are references—not unbounded prompt input.

## Phase 1 — Canonical plan compilation and compatibility

### Task 1.1 — Define the canonical authored-plan contract

**Status:** `done`

**Context:** The rich MDX must be both readable by humans and mechanically executable without maintaining a second abbreviated plan. Preserve prose sections such as decisions, non-goals, file context, task instructions, and evaluation criteria.

**File context:**

- `relay/src/parser/schema.ts`
- `relay/src/parser/parser.ts`
- `relay/src/parser/resolve.ts`
- `relay/src/parser/stringify.ts`
- `relay/src/planning/types.ts`
- New canonical-plan parser/compiler module and fixtures

**Instructions:**

1. Specify a versioned MDX annotation format for plan defaults, phases, steps, phase verification, and gates. It must coexist with normal Mintlify MDX prose and preserve source locations.
2. Define a normalized immutable execution snapshot. Include canonical-document digest, format version, source path, resolved defaults, and a source map from execution fields back to MDX sections.
3. Make phase verification a first-class phase field: an ordered list of `{ cwd, command, label? }`. `cwd` is required for every Node command, even when it matches the phase editing directory.
4. Keep steps focused on implementation instructions and optional inexpensive evidence checks. Do not silently reclassify old step verifies without recording the compatibility behavior.
5. Specify gate semantics such that a normal completed-phase review is exactly one checkpoint. Exceptional pre-start approval remains expressible but cannot create a second adjacent checkpoint.

**Evaluation criteria:**

- [x] Unit fixtures parse a rich MDX plan and retain prose/source-map information.
- [x] Invalid/missing explicit verify CWD, consecutive gates, and unsupported format versions fail with actionable source locations.
- [x] Type tests prove old Relay Markdown and the new canonical snapshot have distinct but supported entry paths.

**Implementation notes:** Added the hidden-comment `relay-plan`/`relay-phase`/`relay-step` MDX contract, a frozen version-1 `CanonicalExecutionSnapshot`, rich fixture coverage, and authoring documentation under `relay/docs/`. Legacy Relay Markdown remains on its existing parser path.

### Task 2.2 — Make phase completion the verification boundary

**Status:** `done`

**Context:** A phase has one implementation agent and may contain several implementation steps. Relay must not claim completion, open a review gate, or commit the phase before its entire verification bundle passes.

**File context:**

- `relay/src/runner/run.ts`
- `relay/src/runner/audit.ts`
- `relay/src/runner/types.ts`
- `relay/src/runner/transcript.ts`
- `relay/src/runner/run.test.ts`
- `relay/src/runner/integration.test.ts`

**Instructions:**

1. Execute implementation steps sequentially; retain nonzero adapter exits as immediate failures.
2. After the last step, execute all phase verification commands exactly once, in order.
3. Capture a phase baseline before the first step. Supply the judge a diff from that baseline before committing, so the review is not blind after `git commit`.
4. Commit only after phase verification and the phase judge pass. Preserve the current explicit branch/alignment safety behavior.
5. Persist phase-level verification results and resume safely if the process stops between verification commands.

**Evaluation criteria:**

- [x] A three-step phase starts three implementation turns, one verification bundle, and no review gate before the final step.
- [x] A failing last verification prevents phase commit and completion.
- [x] The judge input includes the complete phase delta even though the eventual successful phase is committed.

**Implementation notes:** Canonical MDX sources now compile into the runner's execution record while preserving canonical provenance. The runner captures a durable phase Git baseline before its first turn, persists each phase-verification command result as it completes, resumes an interrupted bundle from its successful prefix, and executes the judge against the complete baseline-to-working-tree phase delta before committing. Legacy Markdown stays on its existing step-verification path; phase-level repair semantics remain Task 2.3.

**Status:** `done`

**Context:** The next phase needs more than the last assistant message, but raw transcripts must not grow every future prompt without bound.

Sensitive values and private absolute paths are removed at the persistence boundary. Full patches, raw verification output, logs, and transcripts remain separate run artifacts referenced by relative capsule paths.

## Phase 4 — Contract judging and single-transition gates

### Task 4.1 — Replace the step judge with a phase contract judge

**Status:** `done`

**Context:** The judge is an automated form of human due diligence. It should decide whether the completed phase fulfilled its declared contract, not repeatedly critique partial implementation.

**File context:**

- `relay/src/runner/judge.ts`
- `relay/src/runner/run.ts`
- `relay/src/runner/types.ts`
- `relay/src/adapters/factory.ts`
- `relay/src/runner/judge.test.ts`
- `relay/docs/verification-policy.md`

**Instructions:**

1. Invoke one fresh, read-only judge only after the phase verification bundle passes.
2. Give it the resolved phase contract, completed step instructions, canonical constraints relevant to the phase, phase baseline diff/changed files, verification results, and proposed phase capsule.
3. Require structured output that answers: declared outcomes complete; expected surfaces/files present; scope boundaries respected; verification evidence sufficient; blockers/deviations disclosed.
4. Re-execute any judge-supplied shell checks under the same policy before accepting a pass.
5. Fail if the judge writes to the worktree. A judge verdict failure routes to phase repair, not a false completion.

**Evaluation criteria:**

- [x] A multi-step phase invokes exactly one judge.
- [x] A judge that overlooks a named required surface is rejected by fixture coverage.
- [x] Judge mutation, invalid structured output, and failed judge checks fail safely.

**Implementation notes:** Canonical phases now invoke one fresh, read-only contract judge after the verification bundle passes and before commit. The critic receives the resolved phase contract, step instructions, relevant MDX constraints, baseline diff, verification results, and a proposed capsule. Pass requires structured contract answers plus covering checks for named files, symbols, and routes; Relay re-runs those checks under verification policy. Mutation, invalid JSON/contract output, uncovered surfaces, and failed checks fail closed into phase repair. Legacy Markdown keeps its existing per-step judge.

**Instructions:**
