## Overall context

### Problem

Long agent coding sessions and bounded staging jobs should run on a **Mac Mini M1 (16GB)** so the laptop stays for ideation and review. Today that loop is manual: write a phased markdown plan, run one step, clear the session, repeat, and kick nothing off from a phone.

### What we are building

**Relay** — a plan runner on the Mini, started from phone or laptop, that:

1. Runs a phased markdown plan with a **fresh agent session per phase**.
2. Serves **one** preview chosen at kickoff (Expo **or** web **or** none).
3. Occasionally runs a **bounded staging job** (discovery/curation), then a human **promotes**.

Laptop = ideation, diffs, promote. Each Mini = a worker. Phone = kickoff, gates, preview. v1 is one Mini; the control plane already names **which** machine.

```text
Phone (Relay Expo client) ──┐
Laptop (web console)      ──┼──► machine list ──► Control API on Mini N ──► that Mini’s runner
                            │         │
                            │         └─ (v1: one URL; later: pick relay-1 | relay-2 | …)
                            └── Push / Live Activity
```

### What we are not building

- Another agent, RAG, memory OS, swarm scheduler
- Queues (Temporal, Inngest, Redis) — one run at a time **per machine**
- Docker / K8s / Coolify on this box
- A fleet scheduler or shared run database in milestone 1 (naming the machine is enough)
- A custom tunnel (Tailscale is the tunnel)
- Relay UI inside Just Go or Meridian Go
- Expo Go as the Relay app (evicts product preview)
- Forking `Meridian-Mobile` or `eas init` over `meridian-mobile`
- Native shell as milestone 1, before a `phase-approve` loop works (even with a fake adapter)
- A second git orchestration layer. Do not reimplement `meridian start` / `switch` / lockfile / Events symlink in Relay
- Letting the agent `git checkout`, `git switch`, or `git pull` in `Meridian/` or `Events-Backend/`
- A billing product, vendor-dashboard scraper, or silent account round-robin to farm rate limits
- A second laptop design system. Track D uses BoardUI; do not invent buttons/tables/sidebar beside it

### Should you build the app first?

**No.** The phone app is a remote. The TV is the runner.

Away from the Mini does **not** mean “build iOS first.” It means: **build the harness on the laptop**, talk to it over localhost, treat the Mini as a later deploy target.

Order of value:

1. Parser + state machine + one adapter (fake is fine) + HTTP API — **laptop, now**
2. Web console against that API — **laptop, now**
3. Thin Expo Relay shell against the **same** API — **parallel, not critical path**
4. Cursor adapter + real verify hooks — **laptop, now**
5. Mini bring-up (Tailscale, launchd, profiles, Expo hostname) — **blocked until home**
6. Claude / Codex, promote UI, Live Activities — **after 1–2 work**

Track E (phone shell) in parallel is allowed. Shipping it as the first milestone is not.

| Phone UI | Thin **Expo dev client**, private, `app.relay`. Not Expo Go. Not Just Go. |
| Notifications | Expo Push / APNs from the Mini (ntfy is a fallback, not the product). Live Activity later. |
| Agents | Wrap CLIs. Default Cursor local (`@cursor/sdk`). Also Claude Code, Codex. Explicit per phase. Optional failover. No round-robin. |
| Accounts | Named logins per tool (`cursor:work`, `claude:max`). Kickoff/phase picks one. Failover may try another **account** of the same tool, then another tool. See [Accounts and usage](#accounts-and-usage). |
| Usage UI | Per-login tracker on Home and New run (web + phone). Same `GET /accounts` payload. |
| Preview | User-chosen at kickoff: `expo` \| `web` \| `none`. Agent cannot start Metro. |

| Gates | `step-approve` / `phase-approve` / `full-handoff` / mixed (`approve-before` on a phase). |
| Context | Fresh session per phase. Next phase gets plan slice + `AGENTS.md` + generated `phase-N-brief.md`. Not the prior chat. |
| Version control | **Meridian CLI** for `Meridian/` + `Events-Backend/`. Relay’s runner calls it **before** each agent session. Agents write files and may `git add` / `git commit`. They must not checkout or switch branches. See [Version control](#version-control). |
| Jobs | Staging first. Promote **replays registry/jobs** via existing `/admin/pivot`. Does not re-crawl Heroku. |
| Code home | Sibling `relay/` (or private `Relay`). Must not import Just Go / Meridian app runtime. |
| Trust, don’t build | Meridian CLI, Tailscale, `gh`, Expo, Vite, **BoardUI**, existing pivot admin APIs. |

## Machines

Each Mini is a **machine**: own clone of the workspace, own mutex, own accounts file, own `relay/` process, own MagicDNS name. Runs never move between boxes mid-phase.

| v1 | Later (no rewrite) |
| --- | --- |
| One entry in the client machine list | Add another `{ id, url }` |
| New run hits that URL | New run picks a machine (or the idle one) |
| Usage rows = logins on the **selected** machine | Optional: Home lists every machine, each with its `/accounts` |

Do **not** share one git working tree across Minis. Do **not** put a queue in front of the APIs. A second Mini is another worker you install with the [playbook](#add-a-machine-playbook), then point the phone/web list at it.

Identity: `RELAY_MACHINE_ID` (hostname-safe, e.g. `relay-1`). Every run record stores `machineId`. `GET /machine` returns id, profile, RAM, idle. `POST /runs` may include `machineId`; if the client is already talking to that box’s URL, the server ignores a mismatch and uses itself.

## Version control

Agents in this workspace already do the wrong thing: they edit `Meridian/` and `git checkout` a branch with normal Git. That drifts `Events-Backend`, replaces the `backend/events` symlink with a submodule checkout, and can pin the lockfile to the wrong SHA. [Meridian CLI](/meridian-cli) exists to prevent that. Relay must use it.

### Who does what

| Actor | Allowed | Forbidden |
| --- | --- | --- |
| **Relay runner** (before a phase / on kickoff) | `meridian status`, `meridian start <branch>`, `meridian switch <branch>`, then `meridian symlink`. `MERIDIAN_WORKSPACE` = sibling parent. | Reimplementing checkout. Calling `meridian ship` or `meridian sync` unattended. |
| **Agent** | Write files in the already-checked-out tree. `git add` / `git commit` (“work normally”). | `git checkout`, `git switch`, `git pull`, `git checkout -b`, checking out `backend/events` by SHA, `meridian start` / `switch` / `ship`. |
| **Human** (laptop, after handoff) | `meridian ship`. Merge PRs. Promote. | Expecting Relay to ship. |

Phase briefs must say: you are already on `<branch>` in both repos; do not change branches.

### Branch names

Kickoff chooses a git-safe name. Default: `relay/<slug>/<time>`. No `MER-<number>-<slug>` requirement for Relay runs.

If the branch already exists on remote, Relay **resumes** (`switch` / start-resume), it does not force-create.

Today `meridian start` / `switch` reject non-`MER-*` names. Track B must relax that **for these invocations** (flag or skip the regex). Do not make Relay mint fake ticket branches to appease the CLI. Human interactive `meridian start` can keep the ticket format if you still want it day to day.

### Sibling repos the CLI does not own

`Meridian-Mobile/`, `Meridian-Mintlify/`, `relay/` are separate git checkouts. For those, Relay may use ordinary git (create/switch a branch with the **same slug** when practical). Still the **runner**, not the agent.

A plan that spans backend + mobile: CLI aligns Meridian + Events first; then Relay checks out Mobile. One mutex run, two git tools.

### Unattended CLI

Today `meridian start` prompts on remote branch collision and rejects non-`MER-*` names. Relay cannot sit at a TTY and does not use ticket branches. Child plan for Track B should add **non-interactive flags** on the existing CLI (e.g. `--yes` + `--resume` / fail if dirty) and **accept any git-safe branch name** on those invocations — not a parallel git wrapper. Dirty trees: fail the run (CLI does not auto-stash). After every `start`/`switch`, run `meridian symlink` so Events stays the sibling checkout.

`meridian ship` stays human-only. Relay can mark a run `ready-to-ship` and show `meridian status`; it never merges, never deploys, never updates `private-deps.lock` on its own.

## Accounts and usage

Same tool, more than one subscription or API key, is a **named account** in Relay config (not a second adapter). One run uses one account at a time.

```text
cursor:work     → CURSOR_API_KEY (or sdk apiKey) for that process only
cursor:home     → a second key
claude:max      → CLAUDE_CONFIG_DIR for that login (keep ANTHROPIC_API_KEY unset)
claude:api      → ANTHROPIC_API_KEY on that process only
codex:work      → process env / config dir
```

Kickoff or the phase sets `account`. Failover is an ordered list (`cursor:home`, then `claude:max`). No silent shuffle every phase.

### Usage tracker (UI)

Home and New run show **one row per configured login on the selected machine**, not a pooled bar across Minis.

| Column | Source |
| --- | --- |
| Tool + account name | Relay config |
| This Mini (attributed) | Sum of adapter reports after each phase: tokens / cost / duration when the CLI gives them |
| Vendor remaining | Optional probe the adapter already knows (`claude` usage/status, Cursor usage API if we have a key). `unknown` is allowed |
| Last used | Last run that picked this account |

New run: pick agent **and** account; dim or warn a seat that is exhausted or `unknown`. Run live: show which login is active.

Fake adapter emits fake usage so D/E can ship the strip before Cursor/Claude adapters exist. Do not scrape browser dashboards. Do not store card numbers or vendor passwords in the plan file — secrets stay in Mini config.

## Control API (contract)

All clients use this. Child plans add routes; they do not replace the resource model.

| Resource | Meaning |
| --- | --- |
| `GET /health` | Process up. |
| `GET /machine` | `id`, hostname, profile, RAM, idle. |
| `GET /accounts` | Configured logins **on this machine** + usage snapshot (attributed + vendor remaining or `unknown`). |
| `GET /runs` | List **on this machine**. |
| `POST /runs` | Kickoff: `{ planPath, preview, agent, account?, gate, branch?, machineId? }`. Goal-to-plan generation is deferred to a future planner child; `goal` without `planPath` returns `400`. `branch` is any git-safe name (default `relay/<slug>/<time>`). |
| `GET /runs/:id` | State, phases, preview URL, profile, branch, active account, `machineId`, `meridian status` snapshot. |
| `GET /runs/:id/log` | SSE or poll. |
| `POST /runs/:id/approve` | Gate: phase or plan. |
| `POST /runs/:id/reject` | `{ note }` → appended to next brief. |
| `POST /runs/:id/stop` | Abort agent + keep profile teardown. |
| `POST /runs/:id/preview` | Switch expo/web/none (supervisor, not the agent). |
| `GET /jobs/:id` | Artifact. |
| `POST /jobs/:id/promote` | Requires typed city key (and later Face ID on phone). |

Auth: Tailscale-only network + a shared bearer for the phone/laptop. No public internet.

## Add a machine (playbook)

Copy this into `relay/docs/add-machine.md` when Track G finishes; fill the placeholders. Do not invent a second control plane.

1. **Name it.** Pick `RELAY_MACHINE_ID` (`relay-2`). MagicDNS: `relay-2.tailXXXX.ts.net`.
2. **Tailscale.** Sign the new Mini into the same tailnet. HTTPS (Tailscale cert or Caddy).
3. **Clone.** Own workspace checkout (sibling `Meridian/`, `Events-Backend/`, `Meridian-Mobile/`, `relay/`). Do not NFS-share another Mini’s tree. `npm link` the Meridian CLI. `MERIDIAN_WORKSPACE` = that parent.
4. **Same binary.** Run the same `relay/` as laptop / Mini 1. `launchd` + `caffeinate`. Mutex is local.
5. **Secrets.** Per-box accounts file (Cursor keys, Claude `CLAUDE_CONFIG_DIR`s, Codex). Copy keys if this box should share a seat; do not copy a live OAuth dir from a Mini that is using it.
6. **Push.** Expo / APNs credentials on this box if it should notify.
7. **Clients.** Append `{ id: "relay-2", url: "https://relay-2.tailXXXX.ts.net" }` to the phone and web machine list. Shared bearer (or a new one stored on both clients).
8. **Smoke.** From the phone on tailnet: `GET /machine` → idle, matching id. Kick off a **fake** run, approve, stop. Confirm Home usage rows are this machine’s logins.

Two Minis may run two plans at once (two mutexes). They must not target the same local dirty checkout; they may push different `relay/<slug>/…` branches to GitHub.
