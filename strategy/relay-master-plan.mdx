## How to use this document

This is the **architecture lock** and **parent** for **Relay**. It is **not** a bite-sized task ledger. Do not implement the whole system from this file.

Relay is the product name. Plans have **phases** and **steps** — keep those words. Do not brand this as Meridian, Just Go, Lab, or Pivot Lab.

Child implementation plans (one track or one slice) live as sibling docs in `/strategy`. They must link here and must not invent architecture.

Visual target (phone): [Cursor product language — dark](https://www.figma.com/design/9VS0sCapxoA3crpmzupXnr/Just-GO---new?node-id=91-934) on the `Lab console` page of **Just GO - new** (mocks; on-screen copy should say **Relay**, not Lab). Laptop console is the same API, denser layout, built with **[BoardUI](https://www.boardui.com/)** — not a second product and not a from-scratch kit.

For every **child plan**:

1. Read **Locked decisions** and **Non-goals** in this file first.
2. Cover **one track** (A–K), or one slice of a track — not the whole system.
3. Start the child plan with the [child plan header](#child-plan-header).
4. Work through that child plan’s tasks in order. Update **that** file when tasks complete (same [agent completion](#agent-completion) rules as other strategy plans).
5. When a child plan is created, finished, or blocked, update the [Child plan ledger](#child-plan-ledger) here.

Child plans may add schema fields, API routes, and file lists. They may **not** change Locked decisions without editing **this** file.

## Overall context

### Problem

Long agent coding sessions, quick fixes, repository questions, and bounded staging jobs should run on a **Mac Mini M1 (16GB)** so the laptop stays available for review. Today the phone can kick off an existing plan, but feature-scoped cross-repository planning, read-only questions, small unstructured implementations, checkpoint steering, repository inspection, and product previews still fall back to laptop/SSH workflows and synchronized file paths.

### What we are building

**Relay** — a repository-aware agent control plane on the Mini, started from phone or laptop, that:

1. Answers feature/repository questions in permanently read-only **Ask** sessions.
2. Turns a phone conversation into an explicitly accepted, structured, versioned **Plan** for larger work.
3. Performs quick fixes and small features in **Freeform** on a dedicated multi-repository branch without plan ceremony.
4. Runs accepted plans with a **fresh execution agent session per phase** and keeps a bounded checkpoint session for questions/edits.
5. Serves task-owned Expo/web previews from bounded port leases and exposes principal-scoped read-only repository state.
6. Occasionally runs a **bounded staging job** (discovery/curation), then a human **promotes**.

Phone = Ask/Plan/Freeform conversation, plan revision/kickoff, checkpoint steering, Git overview, and saved-process control. Laptop = quick paste/upload kickoff, detailed logs/diffs, repository/queue management, and promote. Each Mini = the source of truth for its principals, persistent workspaces, queue, leases, sessions, drafts, runs, repositories, and processes. Child #14 keeps one Mini while admitting bounded work for two trusted users.

```text
Phone (Ask + Plan + Freeform + ops) ─┐
Laptop (quick run + review) ┼──► machine list ──► Control API on Mini N ──► drafts / runner / supervisor
                            │         │
                            │         └─ (v1: one URL; later: pick relay-1 | relay-2 | …)
                            └── Push / Live Activity (injected in #7; polling remains complete; live Mini/device later)
```

### What we are not building

- A general-purpose web chatbot, RAG/memory OS, or swarm scheduler. Child #13 Ask/Freeform remain repository-scoped Relay agent modes, not an open-ended assistant platform
- Letting planning conversation mutate code; planning reads the selected product workspace and proposes plan revisions only
- Invisible plan mutation: every executable revision and mid-run amendment requires explicit acceptance
- A raw remote shell, phone-editable executable/argv, or arbitrary command endpoint
- External/distributed queues such as Temporal, Inngest, or Redis. Child #14 adds one small durable local queue for bounded work on one Mini
- Docker / K8s / Coolify on this box
- A fleet scheduler or shared run database in milestone 1 (naming the machine is enough)
- A custom tunnel (Tailscale is the tunnel)
- Relay UI inside Just Go or Meridian Go
- Expo Go as the Relay app (evicts product preview)
- Forking `Meridian-Mobile` or `eas init` over `meridian-mobile`
- Native shell as milestone 1, before a `phase-approve` loop works (even with a fake adapter)
- A second git orchestration layer. Do not reimplement `meridian start` / `switch` / lockfile / Events symlink in Relay
- Letting the agent `git checkout`, `git switch`, or `git pull` in `Meridian/` or `Events-Backend/`
- A billing product, vendor-dashboard scraper, or silent account round-robin to farm rate limits
- A second laptop design system. Track D uses BoardUI; do not invent buttons/tables/sidebar beside it

### Should you build the app first?

**No.** The phone app is a remote. The TV is the runner.

Away from the Mini does **not** mean “build iOS first.” It means: **build the harness on the laptop**, talk to it over localhost, treat the Mini as a later deploy target.

Order of value:

1. Parser + state machine + one adapter (fake is fine) + HTTP API — **laptop, now**
2. Web console against that API — **laptop, now**
3. Thin Expo Relay shell against the **same** API — **parallel, not critical path**
4. Cursor adapter + real verify hooks — **laptop, now**
5. Mini bring-up (Tailscale, launchd, profiles, Expo hostname) — **blocked until home**
6. Structured planning, checkpoint steering, and workspace/process controls — **after the existing runner/API/phone/Mini seams**
7. Claude / Codex, promote UI, Live Activities — **after the core loop**
8. Ask/Plan/Freeform and feature workspaces — **after the shared multi-agent interaction contract**

Track E (phone shell) in parallel is allowed. Shipping it as the first milestone is not.

## Machines

Each Mini is a **machine**: one Relay API/process, one MagicDNS name, a global bounded scheduler, and persistent per-principal workspace bundles. Every principal has independent repository clones and credentials. Runs never move between boxes mid-phase or between principal workspaces.

| v1 | Later (no rewrite) |
| --- | --- |
| One entry in the client machine list | Add another `{ id, url }` |
| New run hits that URL and enters its local queue | New run picks a machine (or the best available one) |
| Usage rows = logins on the **selected** machine | Optional: Home lists every machine, each with its `/accounts` |

Do **not** share one Git working tree across users or Minis. Child #14's queue is local to one Mini and is part of its API process; it is not a fleet scheduler or external service. A second Mini remains another worker installed with the [playbook](#add-a-machine-playbook), then added to the phone/web list.

Identity: `RELAY_MACHINE_ID` (hostname-safe, e.g. `relay-1`). Every run record stores `machineId`. `GET /machine` returns id, profile, RAM, idle. `POST /runs` may include `machineId`; if the client is already talking to that box’s URL, the server ignores a mismatch and uses itself.

## Version control

Agents in this workspace already do the wrong thing: they edit `Meridian/` and `git checkout` a branch with normal Git. That drifts `Events-Backend`, replaces the `backend/events` symlink with a submodule checkout, and can pin the lockfile to the wrong SHA. [Meridian CLI](/meridian-cli) exists to prevent that. Relay must use it.

### Who does what

| Actor | Allowed | Forbidden |
| --- | --- | --- |
| **Relay runner** (before a phase / on kickoff) | `meridian status`, `meridian start <branch>`, `meridian switch <branch>`, then `meridian symlink`. `MERIDIAN_WORKSPACE` = sibling parent. | Reimplementing checkout. Calling `meridian ship` or `meridian sync` unattended. |
| **Agent** | Write files in the already-checked-out tree. `git add` / `git commit` (“work normally”). | `git checkout`, `git switch`, `git pull`, `git checkout -b`, checking out `backend/events` by SHA, `meridian start` / `switch` / `ship`. |
| **Human** (laptop, after handoff) | `meridian ship`. Merge PRs. Promote. | Expecting Relay to ship. |

Phase briefs must say: you are already on `<branch>` in both repos; do not change branches.

### Branch names

Kickoff chooses a git-safe name. Default: `relay/<slug>/<time>`. No `MER-<number>-<slug>` requirement for Relay runs.

If the branch already exists on remote, Relay **resumes** (`switch` / start-resume), it does not force-create.

Today `meridian start` / `switch` reject non-`MER-*` names. Track B must relax that **for these invocations** (flag or skip the regex). Do not make Relay mint fake ticket branches to appease the CLI. Human interactive `meridian start` can keep the ticket format if you still want it day to day.

### Sibling repos the CLI does not own

`Meridian-Mobile/`, `Meridian-Mintlify/`, `relay/` are separate git checkouts. For those, Relay may use ordinary git (create/switch a branch with the **same slug** when practical). Still the **runner**, not the agent.

A plan that spans backend + mobile: CLI aligns Meridian + Events first; then Relay checks out Mobile. One mutex run, two git tools.

### Unattended CLI

Today `meridian start` prompts on remote branch collision and rejects non-`MER-*` names. Relay cannot sit at a TTY and does not use ticket branches. Child plan for Track B should add **non-interactive flags** on the existing CLI (e.g. `--yes` + `--resume` / fail if dirty) and **accept any git-safe branch name** on those invocations — not a parallel git wrapper. Dirty trees: fail the run (CLI does not auto-stash). After every `start`/`switch`, run `meridian symlink` so Events stays the sibling checkout.

`meridian ship` stays human-only. Relay can mark a run `ready-to-ship` and show `meridian status`; it never merges, never deploys, never updates `private-deps.lock` on its own.

## Accounts and usage

Same tool, more than one subscription or API key, is a **named account** in Relay config (not a second adapter). One run uses one account at a time.

```text
cursor:work     → CURSOR_API_KEY (or sdk apiKey) for that process only
cursor:home     → a second key
claude:max      → CLAUDE_CONFIG_DIR for that login (keep ANTHROPIC_API_KEY unset)
claude:api      → ANTHROPIC_API_KEY on that process only
codex:work      → process env / config dir
```

Kickoff or the phase sets `account`. Failover is an ordered list (`cursor:home`, then `claude:max`). No silent shuffle every phase.

### Usage tracker (UI)

Home and New run show **one row per configured login on the selected machine**, not a pooled bar across Minis.

| Column | Source |
| --- | --- |
| Tool + account name | Relay config |
| This Mini (attributed) | Sum of adapter reports after each phase: tokens / cost / duration when the CLI gives them |
| Vendor remaining | Optional probe the adapter already knows (`claude` usage/status, Cursor usage API if we have a key). `unknown` is allowed |
| Last used | Last run that picked this account |

New run: pick agent **and** account; dim or warn a seat that is exhausted or `unknown`. Run live: show which login is active.

Fake adapter emits fake usage so D/E can ship the strip before Cursor/Claude adapters exist. Do not scrape browser dashboards. Do not store card numbers or vendor passwords in the plan file — secrets stay in Mini config.

For accounts that expose a normalized **five-hour (300-minute)** window, Relay checks usage after persisting each completed run step. If strictly less than 10% remains and another executable step remains, the run enters `waiting-for-usage-reset`: repository leases stay held, agent capacity is released, and Relay polls the usage source without invoking a model. At a phase approval gate, the gate remains authoritative and approval cannot dispatch the next phase until usage recovers. Relay resumes the next unstarted step through normal queue/capacity admission only after the same account reports at least 10% remaining. Never interrupt an active step, replay the completed step, silently change accounts, or use the weekly window to drive this pause. Unknown/stale probes remain visible but do not wait forever. Child #14 owns the implementation and recovery contract.

## Plan markdown schema

Formalize the files already written. Child plans must not invent a second format.

An accepted phone draft or laptop upload compiles to this same `Plan` structure. The run always copies an immutable Markdown snapshot into its own data directory.

failover: cursor:home, claude:max    # optional; accounts then tools

# Add crew invites to Just Go

gate: auto
cwd: Meridian/backend
### Step 1.1

  ...

  ...
verify: npm test -- workspace=backend --grep crewInvite

## Phase 2 — mobile UI
gate: approve-before
preview: expo

### Step 2.1

  ...

**Pack for the next phase** (files, not chat):

`cwd` may still point at `Meridian-Mobile` or `Meridian/backend` — that is the **work** repo, not the product name.

## Control API (contract)

All clients use this. Child plans add routes; they do not replace the resource model.

| Resource | Meaning |
| --- | --- |
| `GET /health` | Process up. |
| `GET /machine` | `id`, hostname, profile, RAM, idle. |
| `GET /accounts` | Configured logins **on this machine** + usage snapshot (attributed + vendor remaining or `unknown`). |
| `GET /drafts` / `POST /drafts` | List/create private planning drafts for a chosen product and planning account. Multiple drafts; one active planning response per Mini. |
| `GET /drafts/:id` | Draft metadata, transcript, attachments, revisions, accepted revision, and async planning state. Never return secrets. |
| `POST /drafts/:id/messages` | Persist a planning message/attachments and enqueue one read-only planning response. Questions and revisions are durable; phone may disconnect. |
| `POST /drafts/:id/revisions/:revision/accept` | Explicitly select the executable structured revision. No auto-accept. |
| `POST /drafts/:id/publish` | Propose/confirm repo path, then write and commit locally on the aligned run branch. Never push; run snapshot remains independent. |
| `GET /sessions` / `POST /sessions` | Mode-neutral Ask/Plan/Freeform. Plan create still makes a compatible `PlanDraft`. Clients send configured repository IDs only—never paths, argv, or env. |
| `GET /sessions/:id` | Session, feature scope, transcript, Ask changing-snapshot label, Freeform per-repo review. Never return secrets or `storedPath`. |
| `POST /sessions/:id/messages` | Follow-up. Ask stays read-only on planning capacity. Freeform may mutate after alignment. |
| `POST /sessions/:id/link` | New linked Plan/Freeform from Ask; requires `confirmed`. Never elevates `mode` in place. |
| `POST /sessions/:id/scope-decisions` | Freeform park/accept/reject another configured ID before write. Ask is `403 ask-mutation`. |
| `POST /sessions/:id/stop` / `close` / `recover` / `preview` | Stop/close leave branch changes and never merge/push/discard. Recover does not replay a completed turn. Preview is Freeform supervisor ownership. |
| `GET /runs` | List **on this machine**. |
| `POST /runs` | Kickoff accepts exactly one of `planPath`, inline `plan`, or accepted `draftId`/revision plus preview, execution agent/account, gate, branch, and machine. It persists/returns `queued` immediately, then performs branch/preview/agent work asynchronously while clients poll. Existing path clients remain compatible. |
| `GET /runs/:id` | State, phases, preview URL, profile, branch, active account, `machineId`, `meridian status` snapshot. |
| `GET /runs/:id/log` | SSE or poll. |
| `POST /runs/:id/approve` | Gate: phase or plan. |
| `POST /runs/:id/reject` | `{ note }` → appended to next brief. |
| `GET /runs/:id/checkpoint` | Persistent gate conversation, baseline, owned diff, verification, proposed remaining-plan revision, and recovery state. |
| `POST /runs/:id/checkpoint/messages` | Ask read-only questions or explicitly request a direct code edit in the bounded checkpoint session. |
| `POST /runs/:id/checkpoint/accept` | Accept owned code changes and any separately accepted plan amendment, then resume. |
| `POST /runs/:id/checkpoint/discard` | Restore the checkpoint baseline for session-owned changes only; do not reset unrelated work. |
| `POST /runs/:id/steer` | Persist `{ mode: "next-checkpoint" | "stop-now", message }`; stop-now parks partial state rather than treating it as an ordinary failure. |
| `POST /runs/:id/stop` | Abort agent + keep profile teardown. |
| `POST /runs/:id/preview` | Switch expo/web/none (supervisor, not the agent). |
| `GET /workspace/repos` | Read-only configured repository status and active ownership. No Git mutations. |
| `GET /processes` | Saved manual process profiles plus current owned session/status/log URL. |
| `POST /processes/:profile/start` | Start one configured manual Web/Just Go/Campus profile only while no worker/checkpoint editor is active. |
| `POST /processes/:session/stop` | Stop only the supervisor-owned manual session. |
| `GET /jobs/:id` | Artifact. |
| `POST /jobs/:id/promote` | Requires typed city key (and later Face ID on phone). |

Auth: Tailscale-only network + individual, revocable device sessions resolved to a Relay principal. The phone stores its token in Keychain and gates cold/expired access with Face ID or device passcode for a six-hour local unlock window. The web uses a secure HTTP-only session cookie. No public internet and no bearer embedded in `EXPO_PUBLIC_*` / `VITE_*` configuration.

## Add a machine (playbook)

Copy this into `relay/docs/add-machine.md` when Track G finishes; fill the placeholders. Do not invent a second control plane.

1. **Name it.** Pick `RELAY_MACHINE_ID` (`relay-2`). MagicDNS: `relay-2.tailXXXX.ts.net`.
2. **Tailscale.** Sign the new Mini into the same tailnet. HTTPS (Tailscale cert or Caddy).
3. **Clone.** Own workspace checkout (sibling `Meridian/`, `Events-Backend/`, `Meridian-Mobile/`, `relay/`). Do not NFS-share another Mini’s tree. `npm link` the Meridian CLI. `MERIDIAN_WORKSPACE` = that parent.
4. **Same binary.** Run the same `relay/` as laptop / Mini 1. `launchd` + `caffeinate`. Queue, repository leases, and capacity leases are local to that machine.
5. **Secrets.** Enroll each principal's accounts on that box (Cursor keys, Claude `CLAUDE_CONFIG_DIR`s, Codex, GitHub). Do not copy a live OAuth directory from a Mini that is using it and do not expose one principal's credentials to another.
6. **Push.** Expo / APNs credentials on this box if it should notify.
7. **Clients.** Append `{ id: "relay-2", url: "https://relay-2.tailXXXX.ts.net" }` to the phone and web machine list. Pair each device/browser to an individual principal on the new machine.
8. **Smoke.** From each paired client on tailnet: `GET /machine` → matching id and capacity state. Kick off a **fake** run, approve, stop. Confirm private workspace/account rows and global jobs have the correct visibility.

Each Mini schedules its own bounded workload. Never share a physical working copy across principals or Minis. Different workspace clones may push distinct validated `relay/<slug>/…` branches and open PRs; merge and protected-branch push remain unavailable.
