## Product outcome

A carousel is a named, durable issue belonging to an editorial account. Authors can create many issues, revisit old ones, duplicate an issue, and work across accounts without overwriting a shared tenant slideshow.

The primary creation flow is:

1. Open the issue library and select an editorial account.
2. Choose city picks or a global recap and curate the entire event selection in a configurable search workspace.
3. Review and order the selected events, then continue.
4. Prompt for the issue name **after curation**.
5. Create the issue and open the slide editor with populated, editable slides.
6. Edit, save, and export a specific revision; return to the library later.

The editor should feel like Google Slides: slide thumbnails on the left, a large direct-manipulation canvas in the center, a compact toolbar above, and a contextual inspector for the selected object. Selecting an object should be the primary way to edit it. A large form containing every slide field is not the main interface.

Two editorial formats share the same visual vocabulary:

- **City picks:** an upcoming, themed collection within a city, with an independently chosen hero photograph. A catchy cover title expresses the theme, rather than mechanically listing event names.
- **Sorry you missed it:** a global collection of past events, using recap language and explicit source-city provenance. The format is metadata; it does not force a printed series name onto every slide.

## Decisions and contracts

### Account, issue, and source scope

An **editorial account** is an internal publishing identity such as a city social account or global Just Go magazine. It is not a new login, tenant database, or OAuth integration. Initially platform admins operate these accounts through existing authorization.

Each account has an ID, display name, optional handle, default owner tenant, permitted source tenants, voice defaults, and default format. Each issue retains an owner tenant for compatibility with current authorization/export routing, plus an account ID and stable issue ID. Source events may come from multiple explicitly authorized tenants; ownership and source city are separate concepts. A global account must have an explicitly configured owner tenant rather than an invented `global` database.

An event reference is `(sourceTenantKey, eventId)` with an immutable editorial snapshot and capture timestamp. Never assume ObjectIds alone identify events across city databases. Cross-city selection must not change catalog publication state or consumer Drop membership.

### Document model

Use an additive `schemaVersion: 2` document with stable slide and element IDs. Keep a version-1 renderer available for untouched legacy issues. Store validated data rather than executable CSS/HTML.

| Record | Required content |
| --- | --- |
| Account | Identity, owner scope, allowed sources, defaults |
| Curation draft | Account, format, query/filter specification, selected references, ordered snapshots, optional theme, creation provenance, draft revision |
| Issue | Name, account, owner tenant, format, lifecycle state, curation provenance, current revision, creator/editor timestamps |
| Revision | Immutable resolved document, schema/preset versions, asset references, source snapshots, voice provenance |
| Slide | Stable ID, dimensions, background, ordered elements, preset provenance |
| Element | Stable ID, kind, local position/size, rotation, stacking, visibility, lock state, optional parent/group, content and style |
| Asset | Stable ID/storage key, dimensions, source/credit, ownership, retention references |

Use a logical 1080 × 1350 coordinate space for the initial 4:5 slides. Element positions and dimensions remain independent of editor zoom. Element kinds include text, image, card/group, shape, and sticker. Images keep frame bounds separate from crop focal point/scale. Backgrounds are replaceable, pannable/croppable image layers or solid fills; an author may detach an image background into a movable ordinary image.

### Voice and layout rules

- Resolve shipped, city, account, and issue voice defaults when creating content, with precedence documented and tested. Existing behavior is the baseline; account defaults sit between city and issue defaults.
- Store the resulting text on the element. Every visible text item is editable, including dates, places, labels, cover text, and calls to action.
- Track default provenance for an explicit reset action. Later voice changes never silently rewrite existing issues.
- Distinguish default, custom, intentionally blank, and removed fields. Deletion must not trigger fallback text to reappear.
- Cards begin as **auto-layout groups**: deleting a field removes its gap, and content-sized cards shrink while maintaining padding. Fixed-size cards redistribute only according to an explicit alignment rule.
- Dragging/resizing a card changes its outer geometry while its children can continue to reflow. Moving an individual child explicitly detaches that child into free placement; explain this in the inspector and make it undoable.
- Free-positioned elements stay where the author placed them. Offer an explicit, undoable “Reset layout” rather than silently rearranging a slide.
- Long text remains stored in full. Show overflow and offer resize, reflow, or explicit font fitting; do not silently truncate copy to fit an old manifest limit.

### Approved design baseline

Promote Round 05 covers and the latest Round 06 event slides from `/dev/justgo-cover-lab`:

- Three cover families, each with three variations: Loose letters, Open invitation, and Kept somewhere.
- Three event presets usable with **any** cover: Photo note, On the bill, and In the room. Do not encode one-to-one cover/event pairing.
- Photo note starts with a square photo; On the bill starts with a portrait photo. Both have the approved cream sticker rim, rounded cut edge, subtle sheen, rotation, and layered shadows.
- In the room preserves full-bleed photography and the smaller content-fitted detail card.
- Use the supplied light/dark Just Go die-cut PNGs as editable elements. No enclosing circle. Support insert, duplicate, delete, move, resize, and rotate.
- Preserve saturated photography, orange/cream/ink coherence, Les Flos display lettering, restrained grain, closely grouped titles, and clean corners. Keep full-bleed compositions full bleed.
- Series names and issue numbers are absent by default. The internal issue name does not automatically become printed cover text.
- Borders, shadows, grain, and photo treatments are editable styles. Templates are starting points, not restrictions.

## Phase 1 — A durable issue library

### Step 1.1 — Account and issue persistence

**Status:** `done`

Implementation notes, September 23, 2026:

- `pivot_carousel_accounts` holds the editorial account. Issues are additive fields on `pivot_carousel_decks`: `accountId`, `name`, `format`, `status`, `schemaVersion`, `revision`, `document`, `curation`, and `sources`. Legacy `tenantKey`, `title`, and slides stay.
- Routes under `/admin/pivot/carousel-accounts` create an account, list and open issues, rename, update, duplicate, archive, and restore. Account reads include the 20-slide cap before creation.
- Writes require the revision that was read and return 409 `REVISION_CONFLICT`. Source tenants must be on the account and must be Pivot tenants. The issue owner is the account owner.
- Duplicate copies the issue, assigns new slide and element ids, and keeps asset ids and storage keys.
- Verification: `npx jest --runInBand tests/unit/pivotCarouselIssue.test.js` (3 tests).

**Instructions:**

1. Extend the global carousel data model and register models through existing model services. Add account organization, issue format/status, explicit schema version, and monotonic revision without removing legacy fields.
2. Support paginated account-scoped listing, creation, open-by-ID, rename, duplicate, archive, and restore. Duplicate into an independent document with new slide/element IDs while safely sharing immutable asset references.
3. Require account/owner authorization on every operation; verify allowed source tenants independently. Validate revision on writes and return a conflict instead of last-write-wins.
4. Add indexes for account/status/update order and owner scope. Define bounded document size, slide count, and element limits; initially preserve the existing 20-slide export cap and surface it before creation.

**Evaluation criteria:**

- [x] Two issues in one account and issues in two accounts save independently.
- [x] Unauthorized account/source combinations fail on the server.
- [x] Duplication, archive/restore, stale writes, and invalid documents have meaningful tests.

### Step 1.2 — Library and legacy migration

**Status:** `done`

Implementation notes, September 23, 2026:

- The carousel page stays on the library unless `deckId` is in the URL. A missing id shows an error and does not open another issue. `?deckId=` still opens that deck for export deep links.
- The library switches accounts, searches, and filters by format and status. Cards show a cover thumbnail, name, and last-edited time. New issue creates an account for the city when none exists.
- `POST /admin/pivot/carousel-accounts/migrate` is idempotent. Dry-run is the default. It assigns unowned decks to one `city-default:<tenantKey>` account and does not change `_id`, slides, or `updatedAt`. Rollback is `POST /admin/pivot/carousel-accounts/migrate/rollback` with the report’s `rollback` list, which unsets `accountId` only when it still matches. Default accounts are left in place.
- “Create editable copy” writes a schemaVersion 2 issue and leaves the original on schemaVersion 1. Unknown slide types are kept as unsupported text notes and listed in the response.

Verification: `npx jest --runInBand tests/unit/pivotCarouselMigration.test.js` and `npx jest -c jest.carousel.config.js --testPathPattern=carouselLibrary.test`.

**Instructions:**

1. Make the carousel dashboard entry an issue library with account switcher, search, format/status filters, cover thumbnails, names, last-edited timestamps, and New issue.
2. Open issues by stable URL identity. Preserve tenant/deck/export deep links; missing or unauthorized IDs show an error and library navigation, never another deck.
3. Write an idempotent migration with dry-run reporting that assigns existing decks to default city accounts, preserving IDs, snapshots, layout, timestamps, and existing export references. Do not automatically visually convert them.
4. Offer explicit “Create editable copy” for legacy decks; retain original v1 rendering and export access. Report any unsupported conversion elements rather than silently dropping them.

**Evaluation criteria:**

- [x] Library navigation never overwrites or implicitly opens the latest issue.
- [x] Migration rerun creates no duplicate accounts/issues and has a documented rollback mapping.
- [x] Legacy links and exported artifact access remain functional.

## Phase 2 — Curate first, then name the issue

### Step 2.1 — Configurable search and provider seam

**Status:** `done`

Implementation notes, September 23, 2026:

- Admin search is `POST /admin/pivot/carousel-accounts/:accountId/curation/search`. It reuses catalog eligibility (published, not deleted, pivot custom fields) and `serializeForSlot`. Explore and Drop are unchanged.
- The query spec accepts keyword, include/exclude terms, source tenants, timezone-aware dates, upcoming/past, batch week, tags/categories (any/all, both against `customFields.pivot.tags`), host, venue, image presence, and previously-used-in-account. Price is not a reliable field; only `price=unknown` is accepted. Unknown keys and malformed dates are rejected.
- Default publication is published. `publication=inspect-unreleased` is explicit, labelled on the candidate, and does not publish. Past listings keep `sourceUrl` / `externalLink` and `happenedConfirmed: false`.
- Sort is date, date-asc, relevance (keyword required), or ingested. Pagination is a tie-broken cursor. Global search queries only account sources with concurrency 3 and returns per-source `ok`/`failed` plus `continuation.complete`. Partial results are never marked complete.
- Provider seam: `catalog` v1 now; `vector` returns 501 `PROVIDER_UNAVAILABLE` for Phase 7. Saved searches live on `pivot_carousel_saved_searches`. `GET .../curation/query-spec` is the reset contract; responses include filter chips.
- Verification: `npx jest --runInBand tests/unit/pivotCarouselCurationQuery.test.js` and `npx jest -c jest.carousel.config.js --testPathPattern=carouselCurationQuery.test`.

**Instructions:**

1. Add an admin curation query service, reusing catalog eligibility and serialization where appropriate. Keep consumer Explore/Drop behavior unchanged.
2. Support keyword, include/exclude terms, source city/tenant, explicit date range and timezone, upcoming/past mode, batch week, tags/categories with any/all semantics, host, venue, image presence, and previously-used-in-account filters. Add price/free and other facets only when backed by reliable source fields; represent unknown values explicitly.
3. Default to published, non-deleted events. Any staged/draft inspection must be explicit, authorized, visibly labelled, and revalidated before export; search selection must not publish an event. A past listing alone is not proof it actually happened: retain source links and allow recap review notes.
4. Add sort options (date, relevance when supported, recent ingestion), stable pagination with a tie-breaker, saved searches, filter chips, and reset. Reject malformed dates and unsupported filters instead of silently ignoring them.
5. For global search, query only allowed source tenants with bounded concurrency. Return per-source failure/completeness and deterministic merged pagination; do not present partial results as complete.
6. Define a versioned candidate-provider interface returning event references, snapshots, provenance, optional group ID/theme/reason/score, and query continuation. Implement catalog search now; reserve vector-generated group proposals for Phase 7.

**Evaluation criteria:**

- [x] Filters compose predictably, including any/all tags, date boundaries, unknown values, and exclusion.
- [x] Stable pagination has no duplicates within a result snapshot; failures are visible and retryable.
- [x] Global references retain city identity; cross-tenant access tests pass.

## Phase 5 — Reliable saving and export

### Step 5.1 — Autosave and recovery

**Status:** `pending`

**Instructions:**

1. Debounce document saves with revision preconditions, serialize writes, and show Saving / Saved / Offline / Conflict / Failed states. Never allow an older response to overwrite a newer local edit.
2. Persist a local recovery draft keyed by user/account/issue/schema; offer recovery when it is newer than the server. Do not treat local recovery as a successful server save.
3. On concurrent editing conflicts, preserve both versions and offer reload, compare, or save as a new issue. Real-time collaborative editing is outside this release.
4. Add named revision checkpoints and restore-as-new-revision. Keep immutable revision history separate from the current editable head and define retention before cleanup.

**Evaluation criteria:**

- [ ] Slow/out-of-order responses, network loss, refresh during save, and two-tab conflicts do not lose work.
- [ ] Undo after autosave behaves consistently; export requires a confirmed saved revision.
- [ ] Account switching and sign-out cannot recover another account/user’s draft into the wrong issue.

### Step 5.2 — Exact-revision exports

**Status:** `pending`

**Instructions:**

1. Adapt existing carousel compute jobs to reference an immutable saved v2 revision, resolved voice text, versioned renderer/presets, and stable assets. An edit while a job waits must not make that export stale or change its output.
2. Keep existing tenant/deck/attempt scoping and artifact verification. Validate account ownership at request time and resolve the authorized owner tenant for existing worker contracts. Introduce contract versions/capability gating if worker payloads change.
3. Reuse the shared renderer; wait for fonts and images, surface missing assets, and export at 1080 × 1350 with no editor controls. External image changes must not mutate historical revisions; ingest or pin approved assets through the existing storage path.
4. Preserve PNG/ZIP downloads, progress, retries, cancellation, expiration messaging, and job history. Link every export back to its exact account, issue, and revision.
5. Keep v1 export working during rollout. Verify discovery/refresh compute jobs remain unaffected.

**Evaluation criteria:**

- [ ] Queue export, edit issue and tenant voice, then complete export: output matches the queued revision.
- [ ] Rotations, crop, sticker shadows, grain, custom text, and reflow match browser previews at full resolution.
- [ ] Authorization, missing assets/fonts, cancellation/retry, worker incompatibility, and artifact download regressions are covered.

## Explicit scope boundaries

Initial delivery includes the issue library, account organization, curation-before-editor flow, all approved designs, direct editing, field removal/reflow, image/card/background transformations, editable stickers, autosave/recovery, and exact-revision exports.

Real-time multiplayer, comments/approval workflows, scheduled social posting, OAuth-connected social accounts, arbitrary animation/video, a full Google Slides feature clone, and live vector grouping are not required for this release. Account identity is organizational; no automated external publication is implied.
